# 03. 클라이언트 측 암호화 설계

## 목적과 위협 모델

**목적**: 서버가 해킹당해도 암호화한 파일의 내용을 볼 수 없게 한다.

| 상황 | 보호 여부 |
|---|---|
| 해커가 서버의 파일·백업을 탈취 | 보호됨 (서버에는 암호문만 있음) |
| 해커가 서버를 장악한 채 머물며 암호화 페이지 코드를 조작 | **조작 이후 입력하는 비밀번호는 탈취 가능** (웹 기반 암호화의 근본적 한계) |
| 파일명 | 보호 안 됨 (노출 허용으로 결정) |
| 암호화하지 않은 일반 파일 | 보호 안 됨 |

정말 중요한 파일은 PC에서 `age` CLI로 직접 암호화해 일반 업로드하는 방식을 병행한다. 형식이 같아 서로 호환된다.

## 동작

- **형식**: [age](https://age-encryption.org) passphrase(scrypt) 방식, 확장자 `.age`
- **브라우저 구현**: age 공식 JavaScript 구현(typage v0.3.1 릴리스 단일 파일)을 **게이트웨이에서 직접 제공** (외부 CDN 사용 안 함, 체크섬은 `gateway/web/static/vendor/README.md`)
- 암호화 계산(scrypt)은 화면이 멈추지 않도록 Web Worker(`vault-worker.js`)에서 스트리밍으로 처리
- 파일 입출력은 Quantum API를 쿠키 인증으로 호출 (10MB 단위 분할 업로드)
- **비밀번호**: 서버로 전송하지 않음. 저장하지 않음. 작업할 때마다 입력

### 암호화 업로드
```
파일 선택 → 비밀번호 입력(2회 확인) → 브라우저에서 암호화 → Quantum API로 지정 폴더에 <원래이름>.age 업로드
```

### 복호화 다운로드
```
.age 파일 선택(폴더 탐색) → Quantum API로 다운로드 → 비밀번호 입력 → 브라우저에서 복호화 → 원본 이름으로 저장
```

Quantum에서 `.age` 파일은 일반 파일로 보이며, 미리보기는 되지 않고 이름 검색은 된다. Quantum 수정은 없다.

## 비밀번호 정책

- **분실 시 복구 불가.** 서버도 개발자도 복구할 수 없다.
- 하나의 마스터 비밀번호를 쓰는 것을 권장 (파일마다 다르면 관리 불가)
- 암호화 시 최소 길이 검사 (12자 이상)

## 보안 요구사항 (암호화 페이지)

- 엄격한 CSP: `default-src 'self'`, 인라인 스크립트 금지, 외부 리소스 금지
- 번들한 JS 라이브러리는 버전 고정, 저장소에 체크섬 기록
- 비밀번호 입력란 `autocomplete="off"`
